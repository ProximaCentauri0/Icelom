# 求解器协议（`icelom_solver.exe` ↔ 调用方）

> 适用对象：想直接驱动求解器的脚本/Agent，以及要改 `icelom_solver.cpp` 的人。
> 与之配套的实现细节见 [`算法说明.md`](算法说明.md) 第 2–3 节；本文档只讲**接口契约**。
>
> 一句话：**一次性进程**——启动它，往 stdin 写一个 JSON 再关掉 stdin，然后逐行读 stdout 的
> JSON Lines；进程**永远以退出码 0 结束**（连协议错误也是 0），所以**必须解析输出记录，不能看退出码**。

## 1. 调用方式

```powershell
icelom_solver.exe < puzzle.json          # 二进制本身不接受任何命令行参数
```

- stdin：整个 JSON（UTF-8），读到 EOF 才开始求解。
- stdout：JSON Lines，每行一条记录，逐行 flush（GUI 靠这个边求解边画解）。
- stderr：诊断信息，**不属于协议**。环境变量开关（只影响诊断输出，不改变任何判定）：
  - `ICELOM_DUMP=1`：无解诊断时额外导出最深现场的边集 JSON；
  - `ICELOM_DEBUG_SLOTS=1`：输出解路径上每个编号穿越的位次；
  - `ICELOM_FORCE_KIND=0..7`：**只跑第 k 个 D4 朝向的盘面**（回归测试用：验证 8 个变换的
    正/逆坐标映射，见 `tests/run_tests.py` T15）；
  - `ICELOM_DIAG_ON_ABORT=1`：超时中止时也打印"最深现场"盘面（诊断难例用）。

  > **调用方注意**：stderr **非空不等于失败**。搜遍全树仍无解时会打印
  > `[unsat-diag] 完整搜索无解…` + 最深现场盘面 + 开放端点，这是**正常结论的附带信息**
  > （`done.count == 0` 才是结论）。判"求解器出错"只能看**非零退出码**。
  > GUI 把诊断收起来放在 **查看 → 求解器诊断…**（Ctrl+D），不弹模态框。

  > 求解器只有**一个固定的分支顺序**，没有需要抽样/对照的剪枝旋钮，所以没有配套的调试开关。

## 2. 输入字段（全部）

```jsonc
{
  "w": 9, "h": 9,                                  // 必填, 1..64（超限报错）
  "cells": ["w","i", ...],                         // 必填, 长度必须 = w*h, 行主序 index = y*w+x
                                                   //   "w" = 白格, "i" = 冰格（其它值报错）
  "numbers": [{"x":3,"y":0,"n":6}, {"x":0,"y":2,"n":-2}],
                                                   // 可选。n > 0: 已知数字(1..1000, 可跳号但不可重复)
                                                   //        n = -2: "?" 格(数字未知的编号格)
                                                   //        同一格不能放两个数字
  "in":  {"x":0,"y":4,"side":"L"},                 // 必填。side ∈ R/D/L/U: 进入方向 = side 的反方向
  "out": {"x":8,"y":4,"side":"R"},                 // 必填。side ∈ R/D/L/U: 离开方向 = side 方向
                                                   //   省略/为 null 的 side = 内部 IN/OUT(线路以格心为起/终点)
                                                   //   内部且落在**冰格**上时, 可再加 "dir" 指定滑行/抵达方向
                                                   //   (省略则逐个枚举); 内部落在**白格**上时没有方向概念,
                                                   //   给了 "dir" 也会被忽略(白格可任意转身)
  "edges": [{"x":2,"y":4,"side":"R","kind":"arrow","dir":"R"}],
                                                   // 可选。side ∈ R/D/L/U; kind ∈ segment|arrow|wall
                                                   //   arrow 必须带 dir, 且方向须沿该边的行进轴
                                                   //   边框上的标记只有落在 IN/OUT 的入框/出框边上才有意义;
                                                   //   内部 IN/OUT 没有入框边 ⇒ 它旁边的边框标记一律忽略
                                                   //   (线路本来就不越出边框, 那些标记恒满足)
  "options": {"cover_all_whites": true, "symmetry_retry": false},
  "limits":  {"mode": "unique", "max_solutions": 20, "time_limit_ms": 120000}
}
```

### 2.1 `options`

| 键 | 默认 | 语义 |
| --- | --- | --- |
| `cover_all_whites` | `true` | 要求**所有白格**都被线路经过（官方规则）。关掉后只要求"编号格 + 冰上编号"被覆盖 |
| `symmetry_retry` | `false` | **已废弃（接受但不生效）**：旧版用它表示"第一轮没出结论时再换逆向扫描序搜一遍"。求解器现在是**单颗搜索树 + 单一固定顺序**，不再有任何换序/换朝向重试，该字段**根本不会被解析**（`load()` 只读 `cover_all_whites` / `start_ice_free`）；写进文档只为说明"调用方发了它也没关系" |
| `start_ice_free` | `false` | **已废弃**：旧 v1 的实验开关，现在**解析但完全不参与判定**；保留只为兼容旧请求，不要使用 |

### 2.2 `limits`

| 键 | 默认 | 语义 |
| --- | --- | --- |
| `mode` | `"all"` | `"first"` = 只找一个解；`"unique"` = 判定唯一性；`"all"` = 枚举全部解（受上限约束） |
| `max_solutions` | `2000000` | 仅在 `all` 下有实际意义；达到上限即中止并令 `aborted = true` |
| `time_limit_ms` | `120000` | 整次求解的时限（每 256 个搜索节点检查一次；传播内部也查，不会卡死） |

> **旧协议兼容**：`limits.mode` 缺失且 `max_solutions == 1` 时按 `unique` 处理（历史行为）。
> `mode` 给未知字符串时按 `all`。

## 3. 输出记录

```jsonc
{"type":"solution","index":0,"path":[[0,4],[1,4], ...]}         // 每个解一行; index 从 0 起
{"type":"done","count":1,"nodes":102039,"ms":21.4,"aborted":false,"reason":"..."}
{"type":"error","message":"数字须为 1..1000，问号格写 -2"}
```

| 记录 | 字段 | 说明 |
| --- | --- | --- |
| `solution` | `index`, `path` | `path` 是**逐格序列**，冰格被十字交叉时会**重复出现**（如 `…,(1,1),…,(1,1),…`）；终点为 OUT 格 |
| `done` | `count`, `nodes`, `ms`, `aborted`, `reason?` | `reason` **仅**在 `count == 0` 且解析期已判定结构性无解时出现 |
| `error` | `message` | 输入非法；此时不会再输出 `done`（为保险，实现上仍可能补一条兜底 done 行，调用方应按"收到 error 即失败"处理） |

`aborted = true` 的两种情况：**达到解上限**或**到达时限**。它**不代表无解**。
`unique` 模式的结论：穷尽搜索后只找到一个解 ⇒ `count = 1`；找到两个（输出第二条解，
`index = 1`）⇒ `count = 2`；被时限截断而无法证明唯一 ⇒ **保守报 `count = 2` 且 `aborted = true`**
（"未能证明唯一"，不是"确有两个解"）。

## 4. 全部"硬错误"文案（`type = "error"`）

| `message` | 触发条件 |
| --- | --- |
| `输入不是合法的 JSON 对象` | JSON 解析失败，或根不是对象 |
| `缺少 w/h` | `w`/`h` 缺失或不是 JSON 数字 |
| `盘面尺寸须在 1..64` | 尺寸越界 |
| `cells 长度须为 w*h` | `cells` 缺失、不是数组或长度不符 |
| `cells 取值须为 "w"/"i"` | 格子取值不是 `"w"`/`"i"` |
| `缺少 in/out` | `in` 或 `out` 缺失 |
| `in 格式错误` / `out 格式错误` | `x`/`y` 缺失或不是 JSON 数字 |
| `in 位置非法` / `out 位置非法` | 坐标越界 |
| `IN 不在对应边框上` / `OUT 不在对应边框上` | 给了边框 `side` 但该格不在这条边框上 |
| `numbers 格式错误` | 条目缺整数 `x`/`y`/`n` |
| `数字位置越界` | 数字坐标越界 |
| `数字须为 1..1000，问号格写 -2` | `n != -2` 且 `n < 1` 或 `n > 1000`（所以 `n = 0` 也非法） |
| `同一格放了多个数字` | 同一格出现两条 `numbers` |
| `同一数字出现了两次` | 已知数字重复 |
| `edges 格式错误` | 条目缺整数 `x`/`y` |
| `edge 位置非法` | 坐标越界**或 `side` 不是 R/D/L/U** |
| `edge 标记方向指向盘面内部却没有相邻格` | `side` 指向盘外但该格不在这条边框上 |
| `edge kind 须为 segment/arrow/wall` | 未知 `kind` |
| `同一条边被标记了两种不同含义` | 同一物理边被标了冲突含义（等价重复标记会被忽略） |
| `arrow 缺少方向` | `arrow` 没有合法的 `dir` |
| `箭头方向必须与所在边垂直相交（沿行进轴）` | 箭头方向不沿该边的行进轴 |

## 5. 全部"结构性无解"原因（`done.reason`，仅 `count == 0` 时给出）

`墙堵住了 IN 入口`、`墙堵住了 OUT 出口`、`边框上的线段无法被线路经过（线路只能从 IN 进、OUT 出）`、
`边框上的箭头无法被线路按该方向经过`、`数字空缺数超过问号可提供的位次数`、
`内部冰格 IN 缺少方向`、`内部冰格 OUT 缺少方向`

> 前四条与两条"内部冰格 IN/OUT 缺方向"来自解析期；`数字空缺数…` 来自位次模型的计数检查。
> 其余矛盾（强制边撞墙/成环/箭头逆序、冰格无法直行、位次不可能…）都由**统一的传播引擎**
> 在求解时发现，此时只报 `count = 0`（`aborted = false`）而不给 `reason` —— 因为"哪条规则
> 先撞上"取决于传播顺序，写进协议没有意义。排查这类无解请用 `ICELOM_DIAG_ON_ABORT=1`
> 或 `ICELOM_DUMP=1` 看最深现场盘面。

> 边框标记的三分处理：边框**墙**若正好堵住 IN/OUT ⇒ 无解；边框**线段/箭头**只有落在 IN/OUT
> 所在边时才能被满足 ⇒ 其它位置一律无解；能自动满足的一律静默忽略。

## 6. 调用方最小示例（Python）

```python
import json, subprocess

def solve(puz, mode="all", max_solutions=20, time_limit_ms=60000, symmetry_retry=False):
    req = dict(puz)
    req["options"] = {"cover_all_whites": True, "symmetry_retry": symmetry_retry}
    req["limits"] = {"mode": mode, "time_limit_ms": time_limit_ms}
    if mode == "all":
        req["limits"]["max_solutions"] = max_solutions
    p = subprocess.run(["icelom_solver.exe"], input=json.dumps(req).encode("utf-8"),
                       stdout=subprocess.PIPE, stderr=subprocess.PIPE)
    sols, done, err = [], None, None
    for line in p.stdout.decode("utf-8", "replace").splitlines():
        if not line.strip():
            continue
        o = json.loads(line)
        if o["type"] == "solution":
            sols.append([tuple(pt) for pt in o["path"]])
        elif o["type"] == "done":
            done = o
        elif o["type"] == "error":
            err = o
    return sols, done, err
```

（`tests/run_tests.py:16-41` 是同一份逻辑的完整版；GUI 走的是 Popen + 双守护线程 + 60 ms 轮询，
见 `icelom_gui.py:1459-1472`。）

## 7. 改协议时的检查清单

1. 改 `icelom_solver.cpp` 里的解析/校验 → 同步更新**本文档**的字段表与报错表。
2. 新的 `options` 键要给出**默认值**并写进 §2.1；新的 `limits.mode` 要写进 §2.2。
3. 三处边键规范化（求解器 / `icelom_gui.py:Puzzle.edge_key` / `tests/verify.py:edge_key`）必须一致。
4. 加/改规则语义后跑第 5 节闸门：`tests/run_tests.py` → `tests/fuzz_diff.py` →
   `tests/check_engine_pzprjs.py` → `tools/official_check.py`。
5. 报错文案是**被测试断言的**（如 `run_tests.py` T4 断言 `reason` 含 "IN"、T8b 断言重复/非法数字报错），
   改文案要一起改测试。
