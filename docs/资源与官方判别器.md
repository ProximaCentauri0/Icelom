# 资源与官方判别器

> 这一节回答两个问题：**① 这个项目依赖哪些外部资源、它们必须在哪；② 我凭什么相信求解器的答案是对的。**
> 答案是：除了本项目自己的两套独立实现，还有一份**未经修改的第三方引擎**——pzprjs（puzz.link 的官方前端库）
> ——可以对任意解做 `check()` 判定。

## 2. vendored 的官方 pzprjs 引擎

`tools/pzprjs/` 同时是**运行时依赖**和**可重建的源码树**：

| 路径 | 作用 |
| --- | --- |
| `pzpr.concat.js`（786 KB） | 官方库拼接产物，CommonJS 可直接 `require`（末尾 `module.exports = pzpr`）。**所有 JS 工具 require 的都是它** |
| `pzpr-variety/icebarn.js`（31 KB） | icebarn 变体家族（`icebarn` / `icelom` / `icelom2`）定义，注册方式：`pzpr.classmgr.makeCustom(...require(".../icebarn.js"))` |
| `src/`、`src-ui/res/`、`package.json`、`node_modules/pzpr-canvas/dist/candle.js` | 重建所需的**精简源码树**（官方上游 pzprjs 0.12.0，MIT） |
| `dist/js/`（重建输出） | `node tools/build_concat.js` 的产物；重建后由 `taskset.ps1 build-pzpr` 覆盖到上面两个运行时文件 |

### 2.1 为什么要自己拼接

官方构建走 grunt，而 grunt/eslint 会派生子进程；在受限沙箱里跑不通。`tools/build_concat.js`
复刻了 grunt 的 **concat + `<%= %>` 模板替换** 两步（文件清单来自 `src/pzpr.js` 的导出，
模板数据来自 `package.json` / `src/res/failcode.*.json` / `src-ui/res/p.*.json`）。

### 2.2 重建步骤（已验证可复现）

```powershell
powershell -NoProfile -File tools/taskset.ps1 build-pzpr
# = node tools/build_concat.js  +  把 dist/js 产物覆盖到 tools/pzprjs/ 的运行时位置
```

**验证标准**：重建后 `tools/pzprjs/pzpr.concat.js` 的 SHA256 应与重建前一致
（`E059F5…D2A6C`；`icebarn.js` 为 `F0556F…3E85`）。历史上用**完整 67 MB 源码树**拼接得到的就是这两份字节，
所以后来把源码树精简到 `src/ + src-ui/res/ + package.json + candle.js`（约 4 MB）并删掉了
`tests/pzprjs_src/`、`tests/pzprjs.zip`、`tests/.npmcache/`。改完引擎请重跑 `test-all` 与
`official_check.py db039`，确认行为未变。

## 3. 官方判别器

**这是本项目唯一的第三方判据**：本地求解器给出解 → 把解画进 pzprjs 官方题板 → 调官方 `check()`。
有两条入口，按"题面从哪来"选：

```powershell
# ① 基准题（题面 URL 记在 benchmark/manifest.json 里）—— 走官方解码器
python -X utf8 tools\official_check.py <题目id前缀> [解JSON] [时限秒]

# ② 任意 icelom-v1 题面（example/、assets/、自己画的题）—— 直接在官方盘面上设格/边
python -X utf8 tools\verify_solution.py <题面.json> [解.json] --official
#   或只跑官方那一层:
node tools/official_check.js <题面.json> [解.json]
```

### 3.1 入口 ① 的流程（三个文件串起来）

1. `tools/official_check.py`：在 `benchmark/manifest.json` 里按**子串**取第一条匹配题，
   读 `benchmark/puzzles/<id>.json` 与题面 URL。不给解文件时先自己求解（`max_solutions=1`），
   把解规范成 `{"path":[...]}` 写 `analysis/<id>_solution.json`。
2. `tests/probe_qmark.js`：用 `tools/pzprjs` 打开 URL（`new pzpr.Puzzle()` + `puzzle.open(url)`），
   把解序列逐段转成官方题板的 border 坐标、`setLineVal(1)` 画上去，再补上 IN/OUT 的边框线。
3. 调 `p.check()`，打印 `画线边框数: N 官方判定: PASS|<failcodes>`。

### 3.2 入口 ② 的流程（不经过 URL）

`tools/official_check.js` 先用一个同尺寸的**空盘 URL** 让官方引擎把盘面建出来，
再按 `icelom-v1` 逐项设置：`cell.ques = 6`（冰）、`cell.qnum = 数字 / -2`（"?"）、
`bd.arrowin.input(边框)` / `bd.arrowout.input(边框)`（IN/OUT）、`border.setArrow(...)`（箭头），
最后把解画成 `setLineVal(1)` 并调 `check()`。
这样就不必自己实现"题面 → URL"的编码，也就**不依赖 `benchmark/`**（发布版只带这一条）。

已验证结论：

| 题 | 结论 |
| --- | --- |
| db034（10×7，2 个 "?" 在白格上） | **PASS**（该题唯一解的末位是 "?"，证明"首尾不写 ?"只是作者惯例而非官方规则） |
| db039（13×13，4 个 "?" 在冰格上，数字 1,3,…,17） | **PASS**（171 格线路，位次恰为 `1,?(2),3,?(4),…,?(16),17`） |

## 4. 其它官方引擎用法

| 命令 | 用途 |
| --- | --- |
| `node tests/probe_rules.js` | 规则语义探针：在 2×1/2×2/3×2 小盘上画线并调官方 `check()`，确认"冰上转弯（含起终点）"报 `lnCurveOnIce`，即**冰上 IN 必须直行、冰上 OUT 出框必须沿出框方向直行** |
| `node tests/probe_qmark.js <URL> <解JSON>` | 单个解的官方判定（被 `official_check.py` 调用，也可单独用；**只认带 URL 的题**） |
| `node tools/official_check.js <题面.json> [解.json]` | **判定任意 icelom-v1 题面的解**：先开一张同尺寸空盘，再按题面直接设格子的 `ques/qnum` 与边框（`setArrow`/`setLineVal`），最后调官方 `check()`。不需要 URL，因此也不依赖 `benchmark/`；发布版带的就是它 |
| `node tests/dump_cells_url.js <URL>` | 打印每格原始 `qnum/ques`，用于核对 "?" 格（`qnum <= -2`）与冰格（`ques === 6`）的解码 |
| `node tools/dump_cells.js <URL>` | 同上（`tools/` 版本，等价） |
| `node tools/pzprurl2json.js "<URL>" [out.json]` | 官方解码器：URL → `icelom-v1` JSON（GUI 与 `tests/test_url_import.py` 都用它） |
| `node tools/scan_marks.js` | 扫描 `benchmark/manifest.json`，统计整套题面的冰格/数字/“?”格/边标记数量 |
| `python -X utf8 tests/check_engine_pzprjs.py` | 做题规则引擎与官方引擎的 17 状态差分（含 5 个箭头状态，见 [`测试与验证.md`](测试与验证.md) §4） |

### 4.1 官方判定里几条关键语义（已用探针确认）

- 冰格上**不允许转弯**（起终点冰格也不例外）；冰格允许**十字交叉**（4 条线），任何格子出现 3 条线都是分叉违规。
- 白质 OUT "穿过再出框"需要 3 条连接 ⇒ 官方违规；冰质 OUT "垂直穿过 + 出框"共 4 条 ⇒ 官方允许。
- 编号位次规则（`checkNumberOrder`）：线路上的编号格访问依次占第 1,2,3… 位（"?" 格的**每一次穿越**
  也各占一位），已知数字 `v` 必须正好落在第 `v` 位。
- `?` 在官方编码里是 `cell.qnum <= -2`（`ques` 仍决定它是白格还是冰格）——与本地
  `numbers[].n = -2` 一一对应。

### 4.2 ⚠️ pzprjs 只在 pid `icebarn` 侧校验内部箭头

**这条是 2026-09-13 抓出的重要事实**：pzprjs 的 icebarn 变体清单里，两条与内部箭头有关的检查项写作

```js
"checkFollowArrow@icebarn",   // 线路必须顺着箭头方向经过该边 (lrReverse)
"checkAllArrow@icebarn",      // 箭头所在边必须画线 (arNoLine)
```

而 `AnsCheck.makeCheckList()` 用 `pzpr.util.checkpid(后缀, pzpr.pid)` 过滤 `@` 后缀，
`checkpid` 里是**按 pid 字面比较**（`matches[i] === pid`）——于是 pid = `"icelom"` 时这两项
被判为"本变体不适用"而**整条剔除**（`"icelom" !== "icebarn"`），只有 pid = `"icebarn"` 才会执行。

后果：**用 icelom 题面 URL 跑 `check()` 得到的 PASS 完全不能证明箭头方向正确**。
实测（`example/11_20260909_9x9.json` 修复前的 7 个解）：

| pid | 判定 |
| --- | --- |
| `icelom`（题面自己的 pid） | 7 个解全 PASS —— **包括 6 个逆着箭头走的** |
| `icebarn`（同一盘面、同一解） | 只有 1 个 PASS，其余 6 个报 `lrReverse` |

**怎么用**：要拿官方引擎判箭头，就用 **pid `icebarn`** 摆同一盘面（它没有数字位次/"?" 格那套
icelom 特化规则，但箭头语义完全一致；纯箭头题面两者等价）。
`tests/engine_diff_probe.js` 支持 `pid` 与 `arrows` 字段（含箭头的状态自动用 `icebarn`），
`tests/check_engine_pzprjs.py` 的 A1–A5 就是这么做的。
benchmark 里的 65 道题**没有任何边标记**（`node tools/scan_marks.js` 可复核），所以
`official_check.py` 的既有结论（db034/db039 PASS）不受这条影响。

> 顺带一提：`example/11_20260909_9x9.json` 这类含箭头的题面，用 `puzzle.open(url)` 走 icelom pid
> 是**判不出箭头问题的**——这正是"求解器箭头方向失效"长期没被发现的原因之一。
> 现在的守护网是 `tests/verify.py`（独立验证器逐解查 `逆箭头经过`）、
> `tests/run_tests.py` T14 与 `tests/check_engine_pzprjs.py` 的 A1–A5。

## 5. 数据来源（`benchmark/`）

- `db_icelom_raw.json`：从 puzz.link 数据库拉取的**原始记录快照**（68 条，最后发表日期 2026-09-05）。
- `benchmark/decode_all.js`：把原始记录里的 URL 用官方解码器批量解成题面 JSON，产出
  `benchmark/manifest.json`（含 id/来源/URL/尺寸/规模统计/解码状态）与 `benchmark/puzzles/*.json`。
- 68 条中有 3 条是 `v:/` 变体或带 variant 标签（非标准规则）⇒ 65 道标准题进入基准。
- 题面 JSON **保持原值不重编号**（跳号本身携带"两个已知数字之间该夹几个 ?"的信息）。

新增题面：把记录加进 `db_icelom_raw.json` → `node benchmark/decode_all.js` → 重跑
`benchmark/run_benchmark.py` 与 `tests/audit_benchmark.py`。
