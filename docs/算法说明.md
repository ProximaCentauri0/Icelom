## 1. 项目概览

```
编辑谜题 (tkinter 画布)
        │  JSON (icelom-v1)
        ▼
icelom_solver.exe (C++, 子进程)          ← 本文档第 3 章
        │  JSON Lines (流式)
        ▼
GUI 实时显示解 / 画线路
        │
        ├─ tests/verify.py 独立验证每个解  ← 第 5 章（与 C++ 完全独立实现）
        └─ tools/pzprurl2json.js 导入 puzz.link URL ← 第 7 章
```

设计原则：

- **求解与展示解耦**：求解器是纯 stdin/stdout 进程，GUI 崩溃不影响它，反之亦然；
- **剪枝全部是必要条件**：永不误杀正确解，保证枚举完备；
- **交叉验证**：规则有两套独立实现（C++ 求解器 / Python 验证器），测试中互相核对。

## 2. 数据模型与进程协议

### 2.1 求解器输入（stdin，UTF-8 JSON）

```json
{
  "w": 9, "h": 9,
  "cells": ["w","i", ...],
  "numbers": [{"x":3,"y":0,"n":6}, ...],
  "in":  {"x":0,"y":4,"side":"L"},
  "out": {"x":8,"y":4,"side":"R"},
  "edges": [{"x":2,"y":4,"side":"R","kind":"arrow","dir":"R"}, ...],
  "options": {"cover_all_whites": true},
  "limits": {"max_solutions": 1000, "time_limit_ms": 120000}
}
```

| 字段 | 说明 |
| --- | --- |
| `cells` | 长度 `w*h`，行主序 `index = y*w + x`；`"w"` 白格 / `"i"` 冰格 |
| `numbers` | 编号格；`n > 0` 已知数字（**不必连续**，同一数字不可重复，取值 `1..1000`），`n = -2` 为 **"?" 格**（数字未知的编号格）。详见 3.4 |
| `in` / `out` | 边框格 + 外向侧向（`side` ∈ `R/D/L/U`）；**进入方向 = side 反方向，离开方向 = side 方向**；可放白格或冰格 |
| `edges.side` | 标记在格子 (x,y) 的哪一侧（内部边会规范化，见 2.2） |
| `edges.kind` | `segment` 必经 / `arrow` 定向必经（`dir` 为行进方向）/ `wall` 禁行 |
| `options.cover_all_whites` | 是否要求所有白格都被经过（默认 true = 官方规则） |
| `limits` | 解数量上限（达到后中止）与时间上限（ms） |

> 一切 `side` / `dir` 字段（含 `in` / `out` / `edges` 与边框标记）**只接受 `R` / `D` / `L` / `U`
> 四个字母**（`R` = +x、`D` = +y、`L` = -x、`U` = -y），其它取值一律报 `error`。
> 协议里**没有** `N`（上）这类写法：边框格的上侧写作 `"side":"U"`。

### 2.2 边的规范化

同一物理边有多种描述（"格 (2,3) 的 R 侧" = "格 (3,3) 的 L 侧"）。
**约定：内部竖边（V 边）存左格的 R 侧，内部横边（H 边）存上格的 D 侧；外边框存边框格的外向 side。**
GUI（`Puzzle.edge_key`）与验证器（`verify.edge_key`）都做了同样的规范化，
使三方（GUI / 求解器 / 验证器）的边键完全一致。

### 2.3 求解器输出（stdout，JSON Lines，逐行 flush）

```jsonc
{"type":"solution","index":0,"path":[[0,4],[1,4],...]}  // 每个解一行; path 含冰格交叉的重复格
{"type":"done","count":3,"nodes":51322,"ms":51.2,"aborted":false,"reason":"..."}
{"type":"error","message":"数字须为 1..1000，问号格写 -2"}
```

- `reason` 仅在 `count == 0` 且解析期即可判定结构性无解时给出（见 3.3）；
- `aborted = true` 表示达到解上限或超时，结果可能不完整；
- 每行独立 flush，GUI 边求解边显示已找到的解。

## 3. C++ 求解后端

`icelom_solver.cpp`，单文件，无第三方依赖，`g++ -O2 -std=c++17` 编译。
核心是**约束传播（规则 + 单边试连接，推到不动点）+ 固定顺序的增量回溯 DFS**：
每条内部边只有"未定 / 必用 / 禁用"三态，传播把绝大多数题直接在根节点推完，
剩下的才交给"决定某一格的最终连接"的分支枚举（§3.4–3.8）。

### 3.1 自研 JSON 解析器

`struct JV` + `struct JParser`（约 100 行）：

- 递归下降解析 null/bool/number/string/array/object 六种类型；
- 字符串支持全部标准转义，`\uXXXX` 手工转 UTF-8（1~3 字节，覆盖中文消息）；
- 数字用 `strtod`，整数用 `llround` 还原；
- 任何语法错误置 `fail` 标记，顶层校验 `root.t == 5`（必须是 object）。

之所以不用第三方库：单文件分发 + 只需"读一次"的解析（不需要序列化回 JSON）。

### 3.2 盘面与边编码

**格子**：`c = y*W + x`，共 `N = W*H`。

**内部边**（线路一步 = 从一格走到邻格 = 经过一条边）：

```
nV = (W-1)*H                       // V 边总数（竖边，连接左右两格）
V 边 (x,y)-(x+1,y):  e = y*(W-1) + x          // 0 .. nV-1
H 边 (x,y)-(x,y+1):  e = nV + y*W + x         // nV .. nE-1
nE = nV + W*(H-1)
```

辅助数组：

| 数组 | 含义 |
| --- | --- |
| `incE[c][4]` | 格 c 四个方向（R/D/L/U = 0/1/2/3）上的内部边 id；边框方向为 -1 |
| `ea[e], eb[e]` | 边两端的格子 id |
| `eKind[e]` | 0 无标记 / 1 线段 / 2 箭头 / 3 墙 |
| `eDir[e]` | 箭头的行进方向（仅 eKind==2） |
| `est[e]` | 该边的**三态**：未定 / 必用(已用) / 禁用（墙与推理结论都记在这里，见 §3.4） |

方向编码 `0=R(+x) 1=D(+y) 2=L(-x) 3=U(-y)`，`opp(d) = (d+2)&3`。
**轴位图**：`d & 1` —— 横向（R/L）映射 bit0，纵向（D/U）映射 bit1，用于冰格的"每轴至多一次"记账。

### 3.3 输入校验与规范化

`load()` 在搜索开始前完成所有一次性检查，把错误分成三类：

1. **硬性错误** → `{"type":"error"}`：尺寸越界（>64）、cells 长度不符、IN/OUT 不在对应边框上、
   已知数字越界（不在 `1..1000`）、同一数字出现两次、同格多数字、同一边冲突标记、
   箭头方向与边行进轴不垂直等；
2. **结构性无解** → 记入 `unsatReason`，搜索直接跳过（见下）；
3. **可满足的边框标记** → 静默忽略（自动满足）。

**边框标记的三分处理**（线路只能从 IN 进、OUT 出，所以边框标记大多平凡）：

- 边框**墙**：若恰堵住 IN 入口或 OUT 出口 → `unsatReason = "墙堵住了 IN 入口"` 等；
  其它位置的边框墙恒满足（线路本来就不越出边框），忽略；
- 边框**线段**：只有 IN/OUT 所在边能被经过 → 记为自动满足；其它位置 → `unsatReason`；
- 边框**箭头**：方向等于 IN 的进入方向（或 OUT 的离开方向）→ 自动满足；否则 → `unsatReason`。

重复标记的处理：与已有标记**相同**则忽略，**不同**则报错（例如一条边同时是箭头和墙）。

初始化时线段与箭头直接置为"必用"（强制边），墙置为"禁用"，其余交给 §3.5 的传播。

### 3.4 边状态与节点模型

求解器的全部状态就是**每条内部边的一个三值状态**：

```
est[e] ∈ { 未定(0), 必用/已用(1), 禁用(2) }
```

墙、推理推出来的"这条边不可能被用"、以及真正落子的边，全都记在这一个数组里
（历史版本同时维护 `usedE` / `walledE` 两份账本，两者不同步正是"假矛盾"类 bug 的温床）。
所有改动都写进回溯轨迹 `trail`（`(边号, 旧状态)` 的向量），`undoTo(mark)` 逆序还原。

**节点模型**（与官方"白格可用一次、冰格可直穿一次/十字交叉两次"一一对应）：

| 格类型 | 节点 |
| --- | --- |
| 白格 `c` | 一个节点 `c` |
| 冰格 `c` | 两个节点：横轴 `c`、竖轴 `c + N`（十字交叉的两侧互不相连） |

**连接数**（度数）counting：

- 格内边：每个方向最多一条（`incE[c][k]`）；
- **边框边**：边框 IN/OUT 各给所在格记 **1 条连接**（在入框/出框轴上）；内部 IN/OUT
  （JSON 里省略 `side`）没有边框边，按同样的方式记一条**虚拟边框边**（内部冰格由其
  `dir`/变体决定轴，内部白格无轴概念）。

于是"格被线路穿过几次"有一个统一算法：**穿越次数 = 该格连接总数 / 2**
（起点/终点那一次 = 边框边 + 一条格内边；十字交叉 = 两轴各 2 条）。

**格内合法性 `configLegal(c, mask)`**（`mask` = 该格 4 个方向最终要用哪些边）：

| 判据 | 内容 |
| --- | --- |
| 白格 | 总连接数 == 2（必须在线路上的白格：编号格 / IN-OUT 格 / `cover_all_whites` 开启时的所有白格）；其余白格 0 或 2（**绝不出现 1**） |
| 冰格 | **每条轴**的总连接数 == 0 或 2（IN/OUT 轴 = 边框边 + 1 条格内边；被交叉 = 两轴各 2） |
| 已知数字格 | 穿越次数恰好 1（冰格 ⇒ 只能沿一条轴直穿；白格 ⇒ 度数 2） |
| `"?"` 格 | 穿越次数 1 或 2（冰格可十字交叉；白格只能 1）；被计数强制时恰好 2（见 3.11） |

> 与 `tools/deduce.py` 的 `deg_bounds`/`cell_configs` 是同一套判据，只是写法不同：
> deduce.py 逐格分情况枚举（白格 2 / 冰格 0-2-4 / IN-OUT 格 1 或 3 …），求解器把它写成
> "**边框边也算连接**"的节点度数规则，于是"IN 轴恰好 1 条格内边""IN 与 OUT 落在同一格且
> 两轴垂直""内部 IN/OUT 的虚拟边"这些边界情形全都自动落到同一条式子里，不需要分支枚举。

### 3.5 推理规则（推到不动点）

`propagate()` 反复跑下面 5 条规则直到没有任何状态改变（返回 false = 当前状态已经矛盾）：

**R1 格内配置**（`ruleCells`）：枚举该格全部合法配置（未定边最多 4 条 ⇒ 至多 16 种）：

- 一条合法配置都没有 ⇒ **矛盾**；
- 所有配置**共有**的未定边 ⇒ **必用**；
- 任何配置都**不含**的未定边 ⇒ **禁用**。

**R2 相邻已知数字必须连续**（`ruleNums`）：两个已知数字格直接相连 ⇒ 位次差只能是 1，
`|v2 − v1| ≠ 1` 时这条边⇒禁用。（db039 的"9 与 13 相邻"就是这条。）

**R3 连通 / 无环**（`ruleCycles`，**节点级**并查集）：

- 已用边内部成环 ⇒ **矛盾**；
- 一条未定边若两端已经被已用边连通 ⇒ 用它必成环 ⇒ **禁用**。

冰格的两条轴是两个独立节点，所以"十字交叉"不会被误判成成环。

**R4 可达性**（`ruleReach`）：用**格级**并查集（跨轴也连，是节点级连通的**放宽**）算连通块，
线路上的每一格都必须同时能到 IN 与 OUT；到不了 ⇒ 该格不可能落在线路上 ⇒ 它的所有边禁用
（若其中有**已用**边 ⇒ 矛盾）。放宽方向是安全的方向：放宽图里都到不了，真实图上一定到不了。

**R5 已用分量的路径检查**（`ruleComponents`）：每条已用边都必然落在线路上，因此它所在分量
本身必须能通过 3.6 的**路径检查**（方向 / 编号位次 / 端点类型）；分量含 IN 或 OUT 时朝向被钉死。

> 冰段（"冰区里一条直线贯穿段"）不需要单独的规则：R1 的"冰格每轴 0 或 2"会在不动点迭代里
> 自动把"整段必用 / 整段禁用"传播到底（`tools/deduce.py` 的 `build_stems` 是同一件事的显式写法）。
>
> 每条规则都只做**必要条件的判定**（推不出来就不推），因此不会剪掉真解；正确性的最后一道
> 闸门是 3.8 的整条线路还原校验，它与剪枝强度无关。

### 3.6 单边试连接 + 路径检查

这是"把规则推到极限"的主力（与 `tools/deduce.py` 的
`close_by_probe` / `try_connect` / `_chain_ok` 逐条对应）。

**行走规则**（`stepNext` / `walkDir`）——在"某条边被使用"的假设下，沿线走是**确定性**的：

- 进**冰格**：只能沿进入轴直行 ⇒ 对面那条边"必被用"（即使它还没定，也按"用它"继续走）；
  该格或对面格已经没有合法配置 ⇒ 这个方向撞死；
- 进**白格**：沿已经用掉的边继续；若只剩**唯一**一条可用边 ⇒ 那条必被用；否则去路未定 ⇒
  **自由端**，停下；
- 同一格的同一条轴被走两次 ⇒ 成环，撞死；
- 走到 IN / OUT 端点（白质 IN/OUT 格一进入就是端点；**冰质 IN/OUT 格只有沿入框/出框轴进入
  那一次才算端点**，垂直进入时继续直行）⇒ 链到此为止。

**路径检查 `chainOK(链, 起点类型, 终点类型)`**（与官方 `checkNumberOrder` 同一条规则）：

- 链上所有已知数字的 `v − 局部序号` 必须一致（数字必须一个个递增，不能跳跃）；
- 链上箭头边必须与该朝向的行进方向一致；
- 起点是 IN ⇒ 第一个位次必须是 1；终点是 OUT ⇒ 到 OUT 时位次必须已经走到 Vmax
  （**未达最大数字不能碰 OUT**）；
- `"?"` 的每次穿越落在"空缺位次 ∪ Vmax 之后"里（存在一种赋值即可行，见 3.11）。

**单边试连接**（`tryUse` / `tryForbid`）：

- `tryUse(e)`：两端格在"e 被用"的假设下都还有合法配置，且假设下走出来的候选链**有一个朝向**
  通过路径检查 ⇒ e **可以**被用；
- `tryForbid(e)`：禁掉 e 之后两端格都还有合法配置 ⇒ e **可以**不被用。

**试连接规则**（`ruleProbe`，逐格扫、逐方向试）：

- 试"用"不可行 ⇒ 该边**必禁**；
- 试"禁"不可行 ⇒ 该边**必用**；
- 该格剩下的合法走法（每条边要么已用、要么试连可行）里**所有走法都含**的边 ⇒ **必用**。

一有更新就整轮重来，直到一整轮没有任何更新。**全程确定性、无搜索、无递归。**

> **db039 的例子**（同一结论在求解器与 `tools/deduce.py` 里都由代码得出）：
> 9 往左沿冰走廊直行会撞到 OUT，而此时链上的编号穿越只有 9 自己
> （`lo = hi = Vmax − n + 1 = 17 > p1 = 9`）⇒ 违反"未达 Vmax 不能碰 OUT" ⇒ 禁；
> 9 往下则与相邻的已知数字 13 直接相连（差 4 ≠ 1）⇒ 禁。
> 两条都不可行 ⇒ 9 的度数是 2 ⇒ 必连上方与右方。

### 3.7 分支：固定顺序

推不动时（此时每格都还剩 ≥ 2 种合法配置，或只剩"可跳过的冰格"未定）才分支：

1. **选格**（`pickBranchCell`）：按**行主序**找"必须在线路上"的格（编号格 / IN-OUT 格 /
   `cover_all_whites` 下的白格）里第一个还有 ≥ 2 种配置的；若没有，再按行主序找任意这样的格。
2. **分支 = 决定这一格的最终配置**：对它的 4 个方向逐条 `setEdge(e, 配置里有它 ? 必用 : 禁用)`。
   于是各分支互斥且穷尽（"该格的最终连接集合"必然恰是其中一种），而且**每个分支都真的改变了
   状态**（选格时该格还有未定边 ⇒ 不可能原样不动），DFS 不会原地打转。
3. 分支顺序固定、无启发式打分：**不做 MRV（最少可能数优先）**、不做任何"下一步挑哪个方向
   更可能成功"的排序 —— 推理已经把绝大多数题推死，排序优化变得微不足道。

### 3.8 解的还原与校验

没有可分支的格时，从 IN 出发沿**已用边**重建整条线路并逐条校验（`buildAndCheckPath`）：

1. 每一步都必须走已用边；白格恰有 1 条去路；冰格沿进入轴直行；走出盘面（非 OUT 出框）⇒ 失败；
2. 白格只经过一次；冰格同一条轴只穿越一次；已知数字格只穿越一次；`"?"` 格至多两次；
3. 编号位次：已知数字 `v` 必须落在第 `v` 位（含 IN 格上的编号 = 第 1 位、OUT 格上的编号 = 末位）；
   `"?"` 的每次穿越必须落在允许位次上；
4. 箭头边必须按箭头方向经过（**这条是事后兜底**：任何时候出现的逆箭头解都会在这里被拦下）；
5. **所有已用边都必须在这条线路上**（不许有游离段 / 多余的已用分量）；
6. 编号格全部被经过；`cover_all_whites` 时白格全部被经过。

通过 ⇒ 输出一个解；不通过 ⇒ 这个分支是死胡同（记录现场供无解诊断）。这一层使"剪枝不足"
只影响速度、不影响正确性。

### 3.9 初始化 initState

1. 墙（`eKind=3`）⇒ 禁用；线段 / 箭头（`eKind=1/2`）⇒ 必用（"强制边"）；
2. 建位次表与计数推论（见 3.11）；
3. 跑一次 `propagate()`：所有初始矛盾（强制边冲突、墙围死、位次计数不可能…）都在这里暴露。

**箭头方向**由"已用分量 + 路径检查"承担：箭头边在初始化时就是已用边，它的分量在 R5 里被走一遍，
`chainOK` 会检查每一步的行进方向必须与箭头一致；分量最后拼进线路时同样受这条检查约束，
所以"与 IN/OUT 不相连的孤立箭头分量"（`tests/run_tests.py` T14）也不会被漏掉。

### 3.10 枚举与唯一性判定

- `mode=first`：找到一个解即停（`aborted=false`）。
- `mode=all`：DFS 枚举，达到 `max_solutions` 即停并把 `aborted` 置 true。
- `mode=unique`：最多找两个解 —— 找到两个（不同解）⇒ `count=2`；穷尽搜索只有一个 ⇒ `count=1`；
  被时限截断而无法证明唯一 ⇒ **保守报 `count=2` 且 `aborted=true`**（"未能证明唯一"）。
  旧实现用"正/反两个扫描序各搜一遍"来省时间，现已删除（结论按穷尽搜索给出，语义更直接）。

### 3.11 「?」位次模型

官方判据（pzprjs `icebarn` 的 `checkNumberOrder` / `getTraceInfo`）：沿线第 `p` 次**编号格穿越**
上的数字必须 == `p`。把它用到"题面只印了一部分数字"的盘面上，得到一串只依赖题面的结论：

- 已知数字 `v` 必须落在第 `v` 位；第 `p` 位若没被已知数字占用，就只能由 `"?"` 的穿越来填；
- 空缺数 `G = Vmax − 已知数字个数`；`"?"` 能提供的穿越次数 ≤ 白格 `"?"` 数 + 2×冰格 `"?"` 数
  （冰格 `"?"` 可十字交叉两次）⇒ `G` 超过它就是**结构性无解**（`done.reason` =
  `数字空缺数超过问号可提供的位次数`）；
- `Vmax` 之后最多还能有 `问号白格数 + 2×问号冰格数 − G` 次穿越 ⇒ 位次上限
  `slot_max = Vmax + 余量`；
- 位次表 `slotQ[p]`：`p ≤ Vmax` 且 `p` 不是已知数字，或 `Vmax < p ≤ slot_max` ⇒ 该位次只能由
  `"?"` 填。检查函数 `slotAllows(p, nv)`：已知数字 ⇒ `p == nv`；`"?"` ⇒ `slotQ[p]`。

**计数强制**（`initQmarkNeeds`）：第 1..Vmax 位必须被填满 ⇒ **`"?"` 的穿越总数 ≥ G**，
而每个 `"?"` 冰格最多 2 次、每个 `"?"` 白格最多 1 次。于是

```
G >  问号白格数 + 2×问号冰格数        ⇒ 结构无解
G == 问号白格数 + 2×问号冰格数        ⇒ 每个 "?" 冰格都必须十字交叉两次（无余量）
```

> **余量的处理不能想当然**：`G` 落在中间时（`问号白格数 + 问号冰格数 ≤ G < 上限`）只能推出
> "被交叉两次的冰格 `"?"` 至少有 `G − 问号白格数 − 问号冰格数` 个"，**推不出"每个都要两次"** ——
> `1+1` 那种分配同样可能满足。求解器与推导器现在都用上面那条**无余量等式**
> （`tools/deduce.py` 早先写成 `G − 白格"?"数 ≥ 冰格"?"数` 就下结论，已按此修正；
> 65 题基准里只有 db039 命中"无余量"的情形，所以这个差别在实际题面上没有暴露过）。

**已验证实例**（`tools/check_qmark_slots.py`）：db039 的 9 个已知数字 `1,3,…,17` + 4 个 `"?"` 冰格
⇒ `G = 8 = 0 + 2×4` ⇒ 4 个 `"?"` 格全部必须交叉两次；实测解的位次恰为
`1,?(2),3,?(4),…,?(16),17`。

> **没有移植的推导器机制**：`tools/deduce.py` 的 `rule_slots` 还用"两个编号格之间的曼哈顿距离"
> 去卡位次区间（`位次差 ≤ 曼哈顿距离 + 1`）。这条上界**不成立**：格间步数只保证
> `≥ 曼哈顿距离`，绕行会让位次差变大（例：`(0,0)→(1,0)→(1,1)→(2,1)→(2,0)` 五个编号格时
> 位次差 4 > 2 + 1）。求解器因此只保留可证明的部分（位次表 + 链上的 `"?"` 赋值存在性 +
> IN/OUT 边界），不移植该区间传播。

### 3.12 盘面变换与"单颗搜索树"

求解只跑**一颗搜索树、一个坐标系、一个固定顺序**：不做盘面 D4 变换重试、不做多序探测择优、
不做"超时后换逆向扫描序再试"。`options.symmetry_retry` 仍然被接受（旧请求不报错），
但**完全不参与判定**。

抗方向敏感性靠的是**推理本身**：db039 在 8 个朝向下都是 0 分支节点、毫秒级出解
（`tests/run_tests.py` T16 逐个朝向钉住）。

保留的调试/回归开关：`ICELOM_FORCE_KIND=0..7`（只跑第 k 个 D4 朝向的盘面，测试坐标往返用）、
`ICELOM_DUMP=1` / `ICELOM_DEBUG_SLOTS=1` / `ICELOM_DIAG_ON_ABORT=1`（诊断）。
`ICELOM_PASS` / `ICELOM_STATS` / `ICELOM_PROF` / `ICELOM_CONNEVER` / `ICELOM_QPROBE` 随
搜索排序优化一起删除。

### 3.13 复杂度与实测性能

最坏情况仍是指数级（哈密顿型问题 NP-hard），但"规则 + 试连接"的传播把绝大多数题在**根节点**
就推完了 —— 实测**65 道基准题里 35 道 0 分支节点**，另有 24 道只有 1~66 个分支节点，
只有 db048 到 2092 个。

**基准（65 道真实题面，`benchmark/REPORT.md`）**：

| 版本 | 题数 | 唯一解 | 多解 | 无解 | 超时/未判定 | 总耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 旧（逐格 DFS） | 63 | 57 | 1 | 0 | 7 | 594.7 s |
| 路径段并查集 + MRV 选格（**已删除**） | 65 | 64 | 0 | 0 | 1（db039 120 s 无结论） | 61.5 s ~ 184.4 s |
| **规则传播 + 单边试连接（当前）** | **65** | **65** | 0 | 0 | **0** | **≈5 s** |

> ≈5 s 是 65 题 × 3 遍的**总墙钟**，其中每遍约 20 ms 是进程启动/读题开销；求解器自报的
> `ms` 中位数在 **1 ms 量级或更低**（最慢一题 db048 约 200 ms / 2092 个分支节点）。
>
> db039（13×13、146 白格 + 23 冰格、9 个已知数字 + 4 个 `"?"` 冰格）在旧引擎里是唯一的
> 难例：题面朝向下 300 s 搜不出、换朝向才 2~12 s。现在**任何朝向都是 0 分支节点、2 ms 出解**
> （`python -X utf8 tools/official_check.py db039` 仍为官方 `PASS`，171 格线路、位次
> `1,?(2),3,?(4),…,?(16),17`）。

**正确性验证**（详见 README「测试」小节）：
`tests/run_tests.py`（T1–T16，含独立验证器与独立模型交叉验证、"?" 格用例、箭头方向用例、
db039 纯推理回归）、`tests/fuzz_diff.py`（随机谜题与独立走廊收缩模型逐解集交叉核对 +
独立验证器逐个核对）、`tests/audit_benchmark.py`（基准全量双模型交叉核对）、
`tools/official_check.py`（pzprjs 官方引擎判定）。

**超大棋盘上的每节点开销**：传播是"全盘规则 + 逐边试连接"，单节点代价随盘面规模上升
（真实题面 ≤14×14 实测每节点 < 0.1 ms；而 40×40 全白这种**无结构**的哈密顿型实例只有
约 700 节点/秒，时限内到不了结论）。这类实例在旧引擎下同样解不出来（只是节点数更多），
属于"题面本身就是 NP-hard 硬实例"，不在目标场景内。时限仍被严格遵守（传播内部也查时限），
不会卡死。

## 4. 规则语义与官方引擎对齐

为避免"自己发明规则"，关键边界语义用 **pzprjs 官方引擎的 check()** 做了探针实验
（`tests/probe_rules.js`，在 2×1 / 2×2 / 3×2 小盘上画线后调用官方判定）：

| 探针 | 结论 |
| --- | --- |
| 白格直行/转弯 | PASS（基线） |
| 冰上直行 | PASS |
| 冰上转弯（含起点冰格、终点冰格） | `lnCurveOnIce`（违规） |

由此确认：**冰上 IN 出发必须直行、冰上 OUT 出框那一次必须沿出框方向直行穿出**——
求解器的实现与官方语义一致（3.5 节的过滤 1、2、3 与目标格表）。
另据官方判定的度数规则（`checkBranchLine` 禁止任何格出现 3 条线，
`checkCrossOutOfIce` 只允许冰格出现 4 条线）：白质 OUT"穿过再出框"需 3 条连接
→ 官方同样违规，剪枝合法；冰质 OUT"垂直穿过 + 出框"共 4 条连接 → 官方允许，
求解器已支持（见 9. 已知限制第 1 条的历史）。
求解器另保留一个隐藏开关 `options.start_ice_free`（默认 `false`）——它是 v1 时代的实验开关，
**现已废弃**：求解器仍然解析该字段，但它**完全不影响任何判定**（死了的开关，
读进来后从不被使用）。保留它只为接受旧请求不报错，不应再使用。

## 5. 独立验证器 verify.py

`tests/verify.py` 与 C++ **完全独立**地实现了一遍规则判定，输入谜题 + 解路径，
输出违规列表。用于交叉验证求解器的每一个解（测试套件逐解调用）：

1. 起点 = IN 格、终点 = OUT 格；
2. 逐步检查：相邻移动、越界；
3. 冰格转弯：中转格是冰格且 `进入方向 != 离开方向` → 违规；
4. 边规则：边重复（不重叠）、穿墙、逆箭头、越出边框（防御性）；
5. 格规则：白格重复；冰格同轴二次经过（重叠）；**已知数字**的冰格多次经过/被交叉
   （"?" 冰格允许两轴各一次 = 十字交叉穿越两次）；
6. 编号位次：按路径依次给每个**编号格访问**编号（已知数字格每次经过算 1 位、"?" 格的每一次
   穿越也各算 1 位），要求已知数字 `v` 正好落在第 `v` 位（与求解器同一条规则）；
   所有编号格必须至少被经过一次；
7. 覆盖：cover_all 开启时所有白格必须在路径上；
8. 强制边：每条线段/箭头必须被经过（边框上的自动满足）；
9. 冰上 OUT：最后一步必须沿出框方向进入（直行穿出；白质 OUT 可转弯，无此限制）。

注意：求解器在路径中包含"冰格交叉的重复格"（如 `[.., (1,1), .., (1,1), ..]`），
验证器据此重建每次经过的行进轴。

## 6. GUI 前端算法

`icelom_gui.py`，纯 tkinter（无第三方 GUI 依赖；导出图片用 Pillow）。

### 6.1 自适应布局

```
cs    = min((canvas宽-24)/(w+2.4), (canvas高-24)/(h+2.4), 200)，下限 12
offx  = (canvas宽  - w*cs) / 2
offy  = (canvas高  - h*cs) / 2
```

`+2.4` 是留给外置 IN/OUT 标签/箭头与出界短边的边距（每侧 1.2 格）；
上限 200px 只为防止极端小盘面（如 1×1）铺得过大，正常窗口/全屏下盘面会铺满可用空间
（旧版上限 56px 导致全屏时盘面偏小，已移除）。绑定画布 `<Configure>`，
窗口缩放时重算并重绘，网格始终居中。

### 6.2 命中测试

`_hit_test(像素坐标, allow_out=False) → (格x, 格y, 侧向|None)`：把像素换算到格子局部坐标，
若落在边界带（`bz = max(7px, 0.22*cs)`）内则返回最近的侧向，否则返回 None（格子中央）。
`allow_out=True`（做题模式）时允许返回盘面外一格的坐标 —— 这是画 IN/OUT 出界短边所必需的。

### 6.3 边标记交互（两格定边）

- **按下**：线段/箭头/墙工具在格 A 上按下 → 记 `_edge_start = A`（黄色高亮）；
  再按同格取消；Esc 取消；
- **拖动/点击相邻格 B**：`_edge_from_cells(A, B, tool)` 生成标记并把起点重置为 B
  （支持一笔连画多个箭头）；
- `_edge_from_cells`：由 A→B 的行进方向得出**规范化边键**（左格 R / 上格 D 侧）
  与**行进方向**；切换语义 = 同类同向再操作则删除，否则设置（箭头可反向换向）；
- 白/冰与橡皮的**拖涂**：按下时确定本次笔画目标（涂冰/涂白/擦除）并只压一次撤销栈，
  `B1-Motion` 沿途应用，抬笔结束。

### 6.4 做题模式：线段集合 + 规则引擎 + 拖动手势

做题状态是**无向线段集合** `play_edges = {frozenset({(x1,y1),(x2,y2)}), …}`，
端点可以是盘面外一格的虚拟格（仅为 IN/OUT 处的出界短边，且要求线段至少一端在盘面内）。
线段不分方向、不成路径序列 —— 这样才允许"想到哪画到哪、之后再连起来"。

**拖动手势**（对齐 puzz.link 的 line 输入）：

| 动作 | 语义 |
| --- | --- |
| 按下 | 只记录手势起点（可在任意格，包括盘面外一格），不修改状态 |
| 越过第一条边 | 该边已有线 → 本手势为**擦除**模式；否则为**加线**模式 |
| 继续拖动 | 按模式逐格加线/擦线；快速甩动时逐格补齐中间步 |
| 拖回上一格 | **撤销上一步操作**（加线→删、擦除→恢复） |
| 松开 | 结束手势；整个手势只占**一条撤销记录**（首次实际修改时压栈） |

**规则引擎** `check_play_rules(puz, edges, cover_all)` 返回
`(errors, incompletes, complete, route, route_edges)`：从 IN 出发沿线段走一遍（冰格直行、
白格度数 2 则跟随转弯、"?" 每次穿越各占一个位次），并做局部与全局判定。
判定项与 pzprjs `icebarn.js` 的 AnsCheck 清单一一对应：

| 规则引擎 | pzprjs failcode | 档位 |
| --- | --- | --- |
| 分叉 / 白格十字 / 冰格转弯 | `lnBranch` / `lnCrossExIce` / `lnCurveOnIce` | errors |
| 逆箭头 | `lrReverse`（⚠️ pzprjs **只在 pid `icebarn` 侧**校验内部箭头，`icelom` 侧整条跳过 —— 见 [`资源与官方判别器.md`](资源与官方判别器.md) §4.2） | errors |
| 穿墙 | （本项目扩展：icelom 的编辑工具里没有墙） | errors |
| 从非 OUT 处越出边框 | `lrOffField` | errors |
| 数字位次错误 / 冰上数字被多次经过 | `lrOrder` | errors |
| 未连入线路的多余线段 | `lnPlLine` | errors（线路已成解时） |
| IN 处未画线 / 线路尚未到达 OUT | `stNoLine` / `lrDeadEnd` | incompletes |
| 白格/编号格未经过、强制标记未经过 | `cuNoLine` / `nmUnpass` | incompletes |

设计要点：

- **出界短边可选**：边框 IN/OUT 处画不画出界线都算完成 —— 照抄求解器答案（其路径不含
  盘外格）时不会被"少画一节"卡住。冰上 OUT 若从错误方向进入格内则不合法（`errors`）。
- **IN/OUT 在冰格上**：IN 格允许"出发边 + 之后一次垂直交叉"（度数 3），
  OUT 格允许"结束边 + 之前一次垂直交叉"（度数 3）；出发边取"独边"（与成轴的一对区分）。
- **未完成 ≠ 画错**：线路没连到 OUT、白格没走全 ⇒ 只进 `incompletes`（状态栏提示"还差 N 项"），
  真正违反规则的才进 `errors`（线路变橙）。
- "**检查解**"按钮 = 规则引擎判定；"**对照解**"= 与求解器答案比对：
  当前线段必须是**某个解的子集**（不比较方向与起终点、出界短边不参与），
  即"没有画出错误的连接"—— 部分解也判正确，全部画完且合法才算完成（由检查解判定）。

交叉验证：`tests/check_engine_pzprjs.py` 把同一状态分别交给规则引擎与 pzprjs 官方
`check(true)`，17 个状态（正确/分叉/交叉/冰格转弯/越界/位次/游离段/未完成/**5 个箭头方向**）
结论全部一致 —— 含箭头的状态一律用 pid `icebarn` 做官方判定（pid `icelom` 侧 pzprjs 会整条跳过箭头检查）；
`tests/check_engine_examples.py` 对 example/ 全部示例比对求解器答案 + 独立验证器。

### 6.5 IN/OUT 渲染（镜像等长箭头 + 出界线路）

- **边框 IN/OUT 箭头**：IN 指向盘内、OUT 指向盘外，两者关于框线**镜像对称且等长**
  （同一组常数：尾端伸出 `0.30cs + 线宽/2`、头尖伸出 `0.42cs`、箭头头长 `0.24cs`、
  头半宽 `0.20cs`、杆宽 `0.055cs`）—— 早期版本两种箭头用了不同常数，看起来一长一短；
  画布项打 `inout_in` / `inout_out` 标签，测试直接量 bbox 保证等长；
- 标签画在框外（U/D 侧沿轴外推 0.86cs 居中；L/R 侧外推 0.80cs 并上移 0.28cs 避开箭头与线端）；
- **内部 IN/OUT**：格内浅色衬底 + IN/OUT 字样，无箭头；
- 做题线路与解线路都从格心画到格心，IN/OUT 处可沿画出的短边**伸出界外一格**；
  做题线路是逐段圆头线段绘制，**不画端点圆点**。

### 6.6 撤销栈

每次变更前压入**全量 JSON 快照**（`to_json()` 序列化，上限 500 条）：
题面变更压 `{"kind":"puz"}`，做题线段变更压 `{"kind":"play","edges":[…]}`，
求解压 `{"kind":"solve"}`（撤回时打断求解）。谜题状态小（<10 KB），
全量快照换来零损坏风险的实现简单性。

### 6.7 求解子进程管理

- `Popen` 启动求解器，写 stdin 后立即关闭；
- 两个守护线程：一个喂 stdin，一个逐行读 stdout 入 `queue.Queue`；
- UI 侧 `after(60)` 轮询队列：solution 行即时画线，done 行更新状态栏；
- "停止" = `proc.kill()`（求解器被杀属预期，UI 显示"已停止"）。

### 7.2 解码流程

`puzzle.open(url, cb)` 打开 URL 后从棋盘对象提取：

| 目标 | 提取方式 |
| --- | --- |
| 冰格 | `cell.ques === 6` |
| 数字 | `cell.isNum() && cell.qnum >= 0` |
| **"?" 格** | `cell.qnum <= -2`（官方源码：`cell.qnum = ca !== "?" ? +ca : -2`）→ 输出 `{"x":…,"y":…,"n":-2}` |
| IN/OUT | `bd.arrowin / bd.arrowout` 是半格坐标 Address；**横边线 by 为偶数**（0=顶框、2h=底框），**竖边线 bx 为偶数**（0=左框、2w=右框）→ 换算成 (格x, 格y, side) |
| 内部箭头边 | `border.qdir`（UP/DN/LT/RT 常量从对象上读取）+ 半格坐标 → 规范化的 (左格 R / 上格 D) 键 |

**"?" 格的语义**：`?` 不是"白/冰未定"，而是**数字未知的编号格** ——
格子本身由 `ques` 决定是白格还是冰格，只是上面的数字没印出来。由此：
题面数字呈跳号排列（如 1,3,5,…,17），"?" 格补上中间缺的那些数；
**"?" 冰格允许被十字交叉穿越两次，两次可以是两个不同的数**（作者官方示例
`1 → ?(2) → ?(3) → 4`）。判定规则见 3.4（与 pzpr 官方 `checkNumberOrder` 一致：
编号格访问依次占位次，已知数字 `v` 必须落在第 `v` 位）。
导入器直接把这类格写成 `n = -2`（与 pzpr 的 `qnum` 编码一致），不再拒绝；
`benchmark/decode_all.js` 也保留原值（**不再**按排位重编号 —— 跳号本身携带
"两数之间应该夹几个 ?" 的信息）。本仓库 68 条原始记录里有 2 条含 "?" 格：db034（2 个，
在白格上）、db039（4 个，在冰格上，且各被交叉穿越两次）。
`tools/scan_marks.js` 可扫描任意题目集合，统计各题面的冰格/数字/"?" 格/边标记数量。

已验证的等价性：8×8 博客题 URL 解码结果与人工转录**逐格一致**，且求解同为 1 解；
6×6 官方测试 URL 冰格/数字/IN-OUT 全部一致（该 URL 本身是不可解的失败样例数据，
不用于求解验证）。

## 9. 已知限制与设计取舍

1. **"穿过 OUT 格再回来出框"已支持**（旧版限制，已解除）：
   线路允许先垂直交叉穿过冰质 OUT 格一次、之后折返、最后沿出框方向进入并直行穿出
   （与 pzprjs 官方判定一致：穿过 2 边 + 出框 2 边 = lcnt 4，冰格合法；3 条线才是
   lnBranch 违规，故"穿过 + 出框"之外不可能再出现第三种半通过形态）。
   实现上不再限制冰质 OUT 的进出方向，一切交给冰格直行 + 每轴一次规则；
   仅两处必要约束保留：① 白质 OUT 进入后必须沿出框方向出框——这是**算法自动推导**的
   （白格至多一次，穿过再出框需 3 条连接，度数上不可能），并非人为剪枝；
    ② 拐角 OUT 的第二条边框侧不可越出。配套规则见 §3.4 的格内合法性：冰上数字格若兼为 OUT，
    其数字只能由最终出框那一步收集（不可被垂直穿越后再出框）。
    回归测试：`run_tests.py` T9（5×3 穿过再出框，8 解全部经 verify.py 核对）+
    T10（同盘白质 OUT 对照无解）；冰上数字格若兼为 OUT 仍只许整体经过一次（那次就是出框）。
2. **编号位次规则 + "?" 格**：与 pzpr 官方 `checkNumberOrder` 一致 —— 线路上的编号格访问
   依次占第 `1,2,3…` 位（"?" 格的每一次穿越各占一位），已知数字 `v` 必须落在第 `v` 位；
   "?" 冰格允许被十字交叉穿越两次，两次可以是两个不同的数（判据见 §3.4 与 §3.11）；
3. **最大 64×64**：解析期硬限制，防呆；
4. **撤销栈为全量快照**（≤300 条）：以少量内存换实现简单；
5. **导出图片是离屏渲染，不是屏幕截取**：`icelom_render.py` 用 Pillow 在离屏位图上重绘
   （见 6.8），与前台窗口、窗口遮挡无关，只要装了 Pillow 即可；只有 `icelom_gui.py --selftest`
   与 `tests/gui_visual_test.py`（可视化回归）为了拍到真实界面才用 `ImageGrab` 抓屏，
   那几个测试需要可见桌面；
6. **"搜不到" ≠ "无解"**：`done` 行的 `aborted: true` 只表示到时限/被中止。
   `mode=unique` 现在是"穷尽搜索找一个解"：被时限截断时保守报 `count=2, aborted=true`
   （表示"**未能证明唯一**"而非"确有两个解"）。db039 这类题在旧引擎里曾极吃搜索顺序
   （同一颗树换个盘面朝向差 20 倍以上，题面朝向 300 s 搜不出），现在由推理直接推完、
   任何朝向都是 0 分支节点（§3.13）；
7. **"首尾数字不写成 ?" 只是作者惯例，不是官方判定的一部分**：官方 `checkNumberOrder`
   只要求已知数字落在自己的位次上，db034 的唯一解末位就是 "?"（官方引擎判定 PASS）。
   求解器因此不强制这一点；db039 的计数强制（每个 "?" 必须交叉两次）是由
   `已知数字格数 + 2×"?" 冰格数 = 题面最大数字` 推出的，属于规则本身的推论。
